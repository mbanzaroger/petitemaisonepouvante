# E4 — Observabilité : Prometheus, Alertmanager, Grafana et logs corrélés sur Kubernetes

- **Hypothèse à valider** : les métriques RED et la corrélation des logs permettent de détecter une panne et de diagnostiquer une requête ; elles serviront à lire le test de charge (indicateur 3).
- **Critères de succès** : service collecté par Prometheus ; alerte déclenchée lors d'une panne réelle de dépendance puis résolue au retour ; tableau de bord RED provisionné sans clic ; `correlationId` retrouvé dans les logs.
- **Issue** : #21 · **Workflow** : `.github/workflows/exp-e4-observabilite.yml` · **Script** : `experiments/e4/run.sh` · **Run de référence** : [43607558204](https://github.com/mbanzaroger/petitemaisonepouvante/actions/runs/43607558204) (14/11/2026)

## Environnement de test
| Élément | Version |
|---|---|
| Machine | Runner GitHub `ubuntu-latest` (Ubuntu 24.04, 4 vCPU, 16 Go) |
| Cluster | kind, un nœud |
| Supervision | kube-prometheus-stack 93.3.0 (Prometheus Operator, Prometheus, Alertmanager, Grafana), réduit au besoin (`values-kps.yaml`) |
| Service observé | `catalog-service` construit depuis le dépôt (Spring Boot 4.1.2, Micrometer, `/actuator/prometheus`) + PostgreSQL 16 |
| Collecte | `ServiceMonitor` toutes les 10 s ; histogrammes de latence activés (`percentiles-histogram.http.server.requests`) |

## Étapes reproductibles
1. Cluster vide, puis : `docker build -t catalog-service:e4 services/catalog-service && kind load docker-image catalog-service:e4` (le workflow le fait).
2. `experiments/e4/run.sh` :
   1. installe kube-prometheus-stack (mot de passe Grafana généré à l'exécution) ;
   2. déploie PostgreSQL et `catalog-service` (utilisateur non root 65532, système de fichiers en lecture seule, capacités retirées) ;
   3. applique `02-monitoring.yaml` : `ServiceMonitor` + `PrometheusRule` (`TauxErreurEleve` : > 5 % de 5xx sur 1 min pendant 30 s ; `LatenceP95Elevee` : p95 > 300 ms pendant 1 min) ;
   4. provisionne le tableau de bord `dashboard-red.json` (débit, erreurs, p95, mémoire) par un ConfigMap étiqueté `grafana_dashboard` ;
   5. génère une charge continue avec un `X-Correlation-Id` par requête ;
   6. **panne simulée** : la base est arrêtée (`replicas: 0`), la santé du service passe en 503 ; l'alerte doit se déclencher, puis se résoudre quand la base revient ;
   7. vérifie le tableau de bord par l'API Grafana et recherche un identifiant de corrélation dans les logs.

## Résultats obtenus
| Contrôle | Attendu | Obtenu |
|---|---|---|
| Cible `catalog-service` collectée (`up`) | 1 | ✅ 1 |
| Alerte `TauxErreurEleve` pendant la panne de base | déclenchée | ✅ en 91 s |
| Alerte reçue par Alertmanager | 1 | ✅ 1 |
| Alerte résolue au retour de la base | résolue | ✅ en 10 s |
| Tableau de bord RED provisionné | « PME — RED des microservices » | ✅ |
| Logs portant le `correlationId` `e4-verification` | ≥ 1 | ✅ 5 lignes |

- Charge nominale : **155 req/s** sur `/actuator/health`, **p95 ≈ 0,96 ms**, 0 erreur 5xx.
- Pendant la panne : **55,6 % de réponses 5xx** (les requêtes en échec attendent le délai de connexion de 2 s, d'où un débit réduit).
- Délai de détection de 91 s = fenêtre de calcul (1 min) + durée de confirmation (`for: 30s`) : compromis entre réactivité et fausses alertes.
- Exemple de ligne corrélée : `DEBUG [catalog-service,e4-verification] … DispatcherServlet : GET "/actuator/health"`.
- Durées depuis un cluster vide : supervision prête en 37 s, service prêt en 49 s, cible collectée en 119 s, expérimentation complète en 266 s.

## Difficultés rencontrées
- **`runAsNonRoot` refusé** (`CreateContainerConfigError`) : l'image distroless déclarait l'utilisateur par son nom (`nonroot`), que Kubernetes ne peut pas vérifier. Les Dockerfile des 3 services déclarent désormais l'UID numérique `65532`.
- **Niveau de log par variable d'environnement** : `LOGGING_LEVEL_…` est converti en minuscules ; un nom de classe (`DispatcherServlet`) n'est pas reconnu, un nom de package (`org.springframework.web`) l'est.
- **Recherche du tableau de bord** : la recherche par mot-clé renvoyait un tableau de bord fourni par la pile ; la vérification se fait par identifiant (`uid: pme-red`).
- Sans histogrammes activés, Spring Boot n'expose pas les buckets de latence et le p95 est incalculable dans Prometheus.

## Limites identifiées
- Un seul service observé ; la corrélation **entre services** (REST order → catalog, événements RabbitMQ) est implémentée dans les user stories (US5) et vérifiée en staging.
- Logs lus avec `kubectl logs`, non centralisés ; traces distribuées (OpenTelemetry) non testées.
- Alertes non routées vers un canal (courriel, messagerie) : Alertmanager reçoit l'alerte, le routage est à configurer en production.
- La charge générée vise un point d'entrée léger ; la mesure de l'indicateur 3 sur les parcours métier se fera au test de charge JMeter (J4).

## Décision
- [x] **Adopter** Micrometer + Prometheus Operator (`ServiceMonitor`, `PrometheusRule`) + Alertmanager + Grafana : détection d'une panne réelle en 91 s, résolution en 10 s, tableau de bord versionné et provisionné automatiquement.
- [x] **Adopter** la corrélation par `X-Correlation-Id` dans le MDC des logs (déjà présente dans les 3 services).
- [x] **Écarter pour le POC** la pile ELK (Elasticsearch, Logstash, Kibana) : plusieurs Go de mémoire pour un besoin couvert ici par les métriques et `kubectl logs` ; Loki est l'option privilégiée si la centralisation des logs devient nécessaire.
