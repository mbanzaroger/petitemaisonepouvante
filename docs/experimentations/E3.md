# E3 — RabbitMQ sur Kubernetes : saga, idempotence, file de rebut, panne de nœud

- **Hypothèse à valider** : la messagerie ne perd aucun message confirmé et la saga ne traite jamais deux fois le même événement, y compris en cas de crash d'un consommateur, de message illisible ou de panne de nœud.
- **Critères de succès** : rejeu d'un événement sans double décrément de stock ; message illisible routé vers la file de rebut (DLQ) ; aucun message confirmé perdu après la panne d'un nœud puis le redémarrage complet du cluster.
- **Issue** : #20 · **Workflow** : `.github/workflows/exp-e3-rabbitmq.yml` · **Script** : `experiments/e3/run.sh` · **Banc d'essai** : `experiments/e3/e3.py` · **Run de référence** : [43608084946](https://github.com/mbanzaroger/petitemaisonepouvante/actions/runs/43608084946) (14/11/2026)

## Environnement de test
| Élément | Version |
|---|---|
| Machine | Runner GitHub `ubuntu-latest` (Ubuntu 24.04, 4 vCPU, 16 Go) |
| Cluster | kind, un nœud ; stockage `local-path` |
| Broker | RabbitMQ **4.3.4**, 3 nœuds, opérateur officiel `cluster-operator` v2.23.3 (prérequis : cert-manager v1.21.3) |
| Files | **quorum** (réplication Raft sur la majorité des nœuds), `x-dead-letter-exchange`, `x-delivery-limit` |
| Banc d'essai | Python 3.12 + pika 1.3.2, exécuté en Job Kubernetes dans le cluster (connexion par le Service) |
| Stock simulé | SQLite en mémoire reproduisant `stock_item` et `processed_event` de stock-service |

## Étapes reproductibles
1. Cluster vide, puis `experiments/e3/run.sh` (ou pousser sur une branche `exp/E3-*`).
2. Installation de cert-manager, de l'opérateur, puis du `RabbitmqCluster` à 3 répliques (`01-rabbitmq.yaml`).
3. **Saga** (`e3.py saga`) : 200 `OrderPlaced` + 20 doublons exacts (même `eventId`) + 1 message illisible, publiés avec confirmations. Un premier consommateur traite 80 messages puis « plante » en ayant enregistré le 81ᵉ sans l'acquitter ; un second consommateur reprend. Chaque événement est traité dans une transaction qui insère l'`eventId` (clé primaire) **et** décrémente le stock.
4. **Durabilité** : 2 000 messages confirmés, puis 2 000 autres pendant la suppression d'un nœud (`pme-rabbit-server-1`), puis redémarrage des **3 nœuds** ; lecture finale et comptage des identifiants uniques.
5. Inventaire des files (`rabbitmqctl list_queues`) et état Raft (`rabbitmq-queues quorum_status`) dans l'artefact `e3-resultats`.

## Résultats obtenus
| Contrôle | Attendu | Obtenu |
|---|---|---|
| Événements uniques traités | 200 | ✅ 200 |
| Doublons ignorés (20 publiés + relivrés après le crash) | ≥ 21 | ✅ 21 |
| Stock final (1 000 − 200) | 800 | ✅ 800 |
| Message illisible en DLQ | 1 | ✅ 1 |
| File principale vide en fin de saga | 0 | ✅ 0 |
| Messages confirmés retrouvés après panne et redémarrage complet | 4 000 | ✅ 4 000 uniques sur 4 000 reçus |

- Après le crash simulé, **10 messages** (la fenêtre `prefetch`) sont relivrés au second consommateur avec l'indicateur `redelivered` ; celui déjà enregistré en base est reconnu comme doublon.
- Débit de publication **avec confirmation** : 895 msg/s en nominal, 979 msg/s pendant la suppression d'un nœud.
- Cluster prêt en 96 s ; expérimentation complète en 199 s.

## Difficultés rencontrées
- **Opérateur dépendant de cert-manager** (webhooks) depuis la v2 : installation échouée sans lui, puis webhook indisponible quelques secondes après le déploiement (nouvelle tentative de création du cluster).
- **Message empoisonné en boucle** : un `nack` avec remise en file renvoyait le message illisible indéfiniment au consommateur (banc bloqué). Correctif : rejet **sans** remise en file → routage immédiat vers la DLQ. Règle reprise dans les services (`AmqpRejectAndDontRequeueException`).
- **Attente des Jobs Kubernetes** : deux conditions vraies (`SuccessCriteriaMet`, `Complete`) sur les versions récentes ; attente par `--for=condition=Complete`.

## Limites identifiées
- Un seul nœud kind héberge les 3 nœuds RabbitMQ : la panne simulée est une perte de pod, pas de machine.
- Pendant la suppression du nœud, le client du banc était connecté à un autre nœud : aucune reconnexion n'a été nécessaire. La reprise côté client est assurée dans les services par Spring AMQP (reconnexion automatique) et l'outbox (nouvelle tentative de publication).
- Livraison « au moins une fois » : l'idempotence des consommateurs reste indispensable ; elle est testée ici sur un stock simulé, puis dans stock-service sur PostgreSQL.

## Décision
- [x] **Adopter RabbitMQ 4 avec files quorum** : aucune perte, idempotence efficace, DLQ fonctionnelle, cluster opéré par l'opérateur officiel.
- [x] **Règles reprises dans les services** : publication avec confirmations (outbox), accusé de réception manuel après la transaction, `eventId` enregistré dans la même transaction que l'effet métier, message illisible rejeté sans remise en file.
- [x] **Écarter Kafka pour le POC** : la saga a besoin de routage par clé, de rejets message par message et de files de rebut natives, que Kafka n'offre pas sans surcouche ; son intérêt (débit massif, rejouabilité d'un journal) ne correspond pas au volume de commandes d'une boutique spécialisée.
