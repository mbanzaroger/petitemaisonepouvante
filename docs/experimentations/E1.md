# E1 — Exposition sécurisée : Gateway API (Envoy Gateway), cert-manager et Keycloak sur Kubernetes

- **Hypothèse à valider** : l'authentification OIDC et le TLS automatisé s'intègrent proprement dans le cluster, et l'API est protégée dès le point d'entrée.
- **Critères de succès** : certificat émis **et renouvelé** automatiquement ; Gateway joignable en HTTPS avec une chaîne vérifiée ; jeton Keycloak validé (signature JWKS, émetteur, audience) : 401 sans jeton ou avec un jeton altéré, 403 sans le rôle `CUSTOMER`, 200 avec.
- **Issue** : #18 · **Workflow** : `.github/workflows/exp-e1-gateway-keycloak.yml` · **Script** : `experiments/e1/run.sh` · **Run de référence** : [43605318318](https://github.com/mbanzaroger/petitemaisonepouvante/actions/runs/43605318318) (14/11/2026)

## Changement de cap avant l'expérimentation : Ingress NGINX est retiré
Le cadrage prévoyait Ingress NGINX. Vérification faite avant l'expérimentation : le projet communautaire a été **retiré en mars 2026** (dépôt archivé le 24/03/2026, dernière version v1.15.1 du 19/03/2026). Il ne reçoit plus aucun correctif, y compris de sécurité, et le comité de sécurité de Kubernetes appelle à migrer vers **Gateway API**. Ingress NGINX est donc **rejeté sans essai** pour une plateforme commerciale ; l'expérimentation porte sur son successeur : Gateway API implémentée par **Envoy Gateway** (projet CNCF).

## Étapes reproductibles
1. Cluster vide : `kind create cluster --name e1` (ou le workflow : pousser sur une branche `exp/E1-*`).
2. `experiments/e1/run.sh` enchaîne :
   1. Envoy Gateway (installe les CRD Gateway API), puis cert-manager **après** les CRD (sinon le support Gateway API n'est pas activé) ;
   2. `01-pki.yaml` : émetteur auto-signé → certificat d'AC `pme-ca` (10 ans) → `ClusterIssuer` de type CA ;
   3. `02-gateway.yaml` : `EnvoyProxy` (NodePort), `GatewayClass eg`, `Gateway` HTTPS `*.pme.local` annoté `cert-manager.io/cluster-issuer: pme-ca` ; durée volontairement courte (1 h, renouvellement 59 min 30 s avant) pour observer le renouvellement ;
   4. `03-keycloak.yaml` + `realm-pme.json` : rôles `CUSTOMER`, `MODERATOR`, `ADMIN` ; client SPA `pme-web` (code + PKCE S256) et client `pme-tests` (mot de passe direct, tests uniquement) ; mappeur d'audience `pme-api` ; mots de passe **générés à l'exécution** ;
   5. `04-api.yaml` : `HTTPRoute api.pme.local/api` + `SecurityPolicy` : JWT obligatoire (émetteur, audience `pme-api`, JWKS lu en interne sur le service Keycloak) et autorisation par la revendication `realm_access.roles` contenant `CUSTOMER` ;
   6. tests via une redirection de port locale et `curl --cacert` (chaîne vérifiée, sans `-k`).
3. Les preuves (certificat, revendications des jetons, inventaire, durées) sont dans l'artefact `e1-resultats` du run.

## Résultats obtenus
| Contrôle | Attendu | Obtenu |
|---|---|---|
| Appel sans jeton | 401 | ✅ 401 |
| Jeton dont la signature est altérée | 401 | ✅ 401 |
| Jeton valide de `bob`, sans rôle | 403 | ✅ 403 |
| Jeton valide d'`alice`, rôle `CUSTOMER` | 200 + `pong` | ✅ 200 + `pong` |
| Chaîne TLS vérifiée avec l'AC du bac à sable | `Verify return code: 0 (ok)` | ✅ |
| Protocole négocié | TLS ≥ 1.2 | ✅ TLSv1.3, `TLS_AES_256_GCM_SHA384` |
| Renouvellement automatique | nouvelle révision, nouveau numéro de série | ✅ révision 2 → 3 |

- Certificat présenté : SAN `DNS:*.pme.local`, émis par `PME Root CA (bac a sable)`, validité 1 h.
- Jeton d'`alice` : `iss = https://keycloak.pme.local:8443/realms/pme`, `aud = pme-api`, `azp = pme-tests`, `realm_access.roles = [CUSTOMER]`, durée de vie 300 s.
- Durées depuis un cluster vide : Envoy Gateway prêt en 15 s, cert-manager en 32 s, Keycloak et certificat en 74 s, **expérimentation complète en 95 s** (job de 2 min 19 s avec la création du cluster).

## Difficultés rencontrées
- **Composant prévu retiré** (Ingress NGINX) : découvert à la vérification des versions, avant tout essai. Leçon : vérifier le cycle de vie d'un composant au même titre que ses vulnérabilités.
- **Ordre d'installation** : cert-manager ne prend en charge Gateway API que si les CRD existent à son démarrage ; Envoy Gateway est donc installé en premier.
- **Pas de répartiteur de charge en local** : le Gateway reste « non programmé » avec un service `LoadBalancer` ; résolu par un `EnvoyProxy` en NodePort.
- **Émetteur des jetons** : il doit être identique côté Keycloak (`KC_HOSTNAME`) et côté politique de sécurité, alors que les clés JWKS sont lues sur l'adresse interne du service (`KC_HOSTNAME_BACKCHANNEL_DYNAMIC`).
- **Import du royaume** : déclarer des `clientScopes` remplace ceux par défaut (perte de `realm_access`) ; le mappeur d'audience est donc placé directement sur les clients.

## Limites identifiées
- Keycloak en mode développement (base H2, une instance) : en staging et en production, base PostgreSQL et au moins 2 réplicas.
- AC auto-signée : en production, émetteur ACME (Let's Encrypt) avec un nom de domaine public.
- Le flux mot de passe direct (`pme-tests`) n'existe que pour les tests automatisés ; la SPA utilise le flux code + PKCE.
- Le contrôle au Gateway ne dispense pas le service de valider lui-même le jeton (défense en profondeur, US2).
- Limitation de débit non testée ici : elle sera configurée par `BackendTrafficPolicy` et mesurée au test de charge (J4).

## Décision
- [x] **Rejeter Ingress NGINX** : projet retiré, sans correctifs de sécurité depuis mars 2026.
- [x] **Adopter Gateway API + Envoy Gateway** comme point d'entrée : TLS terminé au Gateway, JWT et rôles contrôlés avant d'atteindre les services (voir ADR-003).
- [x] **Adopter cert-manager** : émission et renouvellement automatiques observés, intégration native avec Gateway API.
- [x] **Adopter Keycloak 26** : OIDC standard, rôles du royaume exploitables par le Gateway et par Spring Security.
