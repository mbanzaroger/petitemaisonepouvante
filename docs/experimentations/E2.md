# E2 — Pipeline qualité : JaCoCo, Testcontainers, Trivy, gitleaks (SonarQube Cloud en complément)

- **Hypothèse à valider** : les outils du pipeline mesurent les indicateurs 1 (couverture) et 4 (vulnérabilités) et **bloquent** un livrable non conforme.
- **Critère de succès** : chaque dégradation volontaire fait échouer le contrôle correspondant ; un service conforme passe le pipeline complet.
- **Issue** : #19 · **Workflow** : `.github/workflows/exp-e2-pipeline-qualite.yml` · **Run de référence** : [43604901970](https://github.com/mbanzaroger/petitemaisonepouvante/actions/runs/43604901970) (14/11/2026)

## Environnement de test
| Élément | Version |
|---|---|
| Machine | Runner GitHub hébergé `ubuntu-latest` (Ubuntu 24.04, 4 vCPU, 16 Go), Docker Engine |
| Service testé | `catalog-service` : Spring Boot 4.1.2, Java 21 (Temurin), Maven 3.9.15 (wrapper 3.3.4) |
| Tests | JUnit 5, Testcontainers 2.0.5, PostgreSQL 16-alpine |
| Couverture | JaCoCo 0.8.14, règle `LINE COVEREDRATIO ≥ 0.80` |
| Sécurité | Trivy 0.70 (trivy-action 0.36.0, épinglée par SHA), gitleaks 8.30.1 |
| Alternative | OWASP Dependency-Check 12.2.2 (plugin Maven) |

Bac à sable : chaque cas travaille sur une **copie de travail du runner**. Rien n'est commité ; aucun secret réel n'est utilisé (la clé du cas 4 est générée aléatoirement à l'exécution, ce qui évite aussi le blocage par la protection des secrets de GitHub).

## Étapes reproductibles
1. Créer ou mettre à jour une branche `exp/E2-<nom>` depuis `develop` et la pousser : le workflow démarre (ou *Actions → Expérimentation E2 → Run workflow*).
2. Référence conforme : la CI de la PR #43 construit les 3 services, exécute 4 tests unitaires + 4 tests d'intégration Testcontainers par service, contrôle la couverture et scanne les images.
3. Le workflow E2 exécute en parallèle 4 dégradations et 1 alternative :

| Cas | Dégradation appliquée | Contrôle | Commande |
|---|---|---|---|
| 1 | Classe métier `PrixRemise` de 12 lignes ajoutée sans test | JaCoCo | `./mvnw verify` |
| 2 | Dépendance `commons-text:1.9` ajoutée au `pom.xml` | Trivy SCA | `trivy fs --scanners vuln --severity CRITICAL,HIGH --exit-code 1` |
| 3 | Image de base remplacée par `distroless/java21-debian12` | Trivy image | `trivy image --severity CRITICAL,HIGH --ignore-unfixed --exit-code 1` |
| 4 | Clé d'accès cloud factice dans `application.yml` | gitleaks | `gitleaks dir` |
| Alt. | Aucune | Dependency-Check | `dependency-check-maven:check -DfailBuildOnCVSS=7`, plafond 15 min |

4. Le job « Synthèse » réussit uniquement si les 4 contrôles ont **échoué** comme attendu.

## Résultats obtenus

| Cas | Résultat du contrôle | Bloqué | Durée du job |
|---|---|---|---|
| Référence (PR #43) | 3 × 8 tests verts, contrôle JaCoCo atteint, 0 vulnérabilité critique/haute dans les images | – | build et tests ≈ 50 s par service (en parallèle), pipeline complet ≈ 3 min |
| 1 — couverture | `lines covered ratio is 0.52, but expected minimum is 0.80` → BUILD FAILURE | ✅ | 57 s |
| 2 — dépendance | `CVE-2022-42889` CRITICAL (commons-text 1.9, corrigée en 1.10.0, RCE par interpolation) | ✅ | 12 s |
| 3 — image | 10 vulnérabilités corrigeables : 1 CRITICAL (brotli CVE-2026-111497), 9 HIGH (expat) | ✅ | 69 s |
| 4 — secret | `leaks found: 1` (règle AWS access key) | ✅ | 8 s |
| Alternative | Échec après 41 s : `NVD Returned Status Code: 429`, `No documents exist` | – | 49 s |

**Constat réel pendant la mise en place** : le premier build des squelettes (PR #43) a été bloqué par le cas 3 *sans dégradation volontaire*. L'image `gcr.io/distroless/java21-debian12` n'est plus reconstruite (le projet distroless ne publie plus que Debian 13) et accumule des vulnérabilités corrigées dans Debian. Correction : passage à `java21-debian13:nonroot`, image validée sans vulnérabilité critique/haute.

## Difficultés rencontrées
- **Image de base obsolète** (voir ci-dessus) : le contrôle a fonctionné, mais il a révélé qu'une image « minimale et sécurisée » peut devenir vulnérable si sa branche n'est plus maintenue.
- **Dependency-Check sans clé NVD** : l'API NVD limite fortement les appels anonymes (HTTP 429). Sans clé, la première synchronisation échoue ou dure des heures ; l'outil ne produit aucun résultat exploitable.
- **Testcontainers** exige un démon Docker : disponible sur les runners GitHub, à installer en local (Docker Desktop ou Codespaces).
- **SonarQube Cloud** : nécessite un compte, un jeton (`SONAR_TOKEN`) et la désactivation de l'analyse automatique ; le job Sonar de la CI reste inactif tant que le secret est absent.

## Limites identifiées
- Le Quality Gate SonarQube Cloud (indicateur 2 : dette, duplication) n'est pas encore démontré ; il sera ajouté comme cas 5 dès que le secret `SONAR_TOKEN` sera configuré.
- Trivy ne voit que les vulnérabilités **connues** (CVE publiées) : il ne remplace ni le SAST (CodeQL) ni le DAST (ZAP).
- `--ignore-unfixed` laisse passer les vulnérabilités sans correctif : elles relèvent d'une exception documentée (politique de sécurité §6).
- Les règles gitleaks par défaut détectent les formats de secrets connus ; un mot de passe « maison » de faible entropie peut passer.

## Décision
- [x] **Adopter** JaCoCo (contrôle bloquant dans Maven **et** dans la CI), Testcontainers, Trivy (SCA + image + IaC) et gitleaks : les 4 dégradations sont bloquées, en quelques secondes pour les scans.
- [x] **Rejeter** OWASP Dependency-Check : dépendance à l'API NVD (clé obligatoire, quotas), aucun résultat sans clé, alors que Trivy couvre dépendances, images et IaC avec une base mise à jour sans compte.
- [x] **Adopter** l'image `distroless/java21-debian13:nonroot` et la règle : *une image de base doit appartenir à une branche maintenue* (ajoutée à la politique de sécurité).
- [ ] SonarQube Cloud : adoption confirmée après le cas 5 (Quality Gate en échec sur du code dupliqué).
